# スタディ固有関数から 00-06 文書を生成する Agent 工程作業書

> 本文件是通用内部工程作业书，用于指导 AI agent 或协作者从一个
> **スタディ固有関数文件**生成该スタディ的 00-06 全套 Markdown 文档。
>
> 本文件不绑定任何特定スタディ、医院、机构、癌种、疾病领域或函数文件名。
> 使用时请将 `{STUDY_ID}`、`{FUNCTION_MODULE}`、`{OPERATION_CONF}` 等占位符替换为目标スタディ的实际值。
>
> 本文件不是对外交付文档，不纳入 00-06 文档体系。

---

## 0. 使用前提

### 0.1 本文件定位

- 本文件是研究作业者与 AI / 协作者的内部指导文件。
- 本文件用于把代码事实、内部背景、文档分层规则和验收标准统一成一套可执行流程。
- 本文件可用于任何スタディ，但每个スタディ生成出的 00-06 文档必须独立维护。
- 本文件本身不是纳品物，也不出现在对外交付文档清单中。

### 0.2 适用对象

适用于以下场景：

- 已存在一个或多个スタディ固有 Python 函数文件。
- 需要从代码反向补齐或生成 RD / BD / DD / TM / TE / DP / DR。
- 需要让另一个独立实现者只看 RD / BD 即可复现等价逻辑。
- 需要保留 A/B 实装比对能力，用文档和测试发现现有代码潜在问题。

### 0.3 推荐输入

最少输入：

1. スタディ固有関数文件，例如 `{FUNCTION_MODULE}.py`
2. 本 guide

强烈推荐额外输入：

- 目标スタディ ID：`{STUDY_ID}`
- 连携设置文件名：`{OPERATION_CONF}`，例如 `{STUDY_ID}_OperationConf.xlsx`
- 目标文档输出目录：`{DOC_ROOT}/MarkDown`
- 该スタディ的简短业务背景，限于可对外出现的中性描述
- 必须隐藏的机构名、人员名、内部项目名、敏感背景

### 0.4 Markdown 与 Excel 的关系

- `MarkDown/*.md` 是 source，也是主要编辑对象。
- Excel / xlsx 是后续纳品物，可由 Markdown 统一生成。
- 本 guide 只规定 Markdown source 的生成规则。
- 除非用户明确要求，不修改 Excel。

### 0.5 合规边界

默认只写内部纳品、内部レビュー、追跡可能性。

不得声称：

- 满足 GxP。
- 满足 PMDA / FDA / ICH 等监管提交要求。
- 满足 CDISC SDTM 合规要求。
- 已完成正式验证或最终承认。

可以写：

- Draft Baseline。
- 初版整備済。
- 試験計画策定済。
- レビュー待ち。
- 追跡可能性。

## 1. 内部背景与对外叙事

### 1.1 真实时间线 vs 文档呈现

很多スタディ固有処理的真实情况是：代码先存在，文档事后补齐。

00-06 文档呈现时仍应按 V 字模型组织：

```text
01 RD → 02 BD → 03 DD → 実装 → 04 TE → 05 TM → 06 DR
```

这不是伪造事实，而是用标准工程结构整理已有事实和后续验证路径。

### 1.2 双重身份风险

如果同一个人既写现有代码，又写 RD / BD，就存在结构性风险：

- RD / BD 可能不自觉地按现有代码倒推。
- B 组实现者会被规格锁死，无法发现 A 组代码问题。
- A/B 输出一致可能只是“规格强迫一致”，不代表代码正确。

因此：

- RD / BD 写业务意图和外部契约。
- DD / TE / TM 才写现行实现细节。
- 现行实现与业务意图存在差异时，必须作为测试检知点保留。

### 1.3 A/B 独立实现结构

推荐把文档体系设计成支持 A/B 比对：

- A 组：现有代码及其 DD / TE。
- B 组：只读 01 RD 和 02 BD，独立实现。
- A/B 对同一输入数据输出一致：支持现有实现。
- A/B 在边界数据或前提違反数据上输出不同：用于发现业务前提、规格歧义或代码潜在 bug。

### 1.4 代码契约 vs 连携设置契约

必须区分：

| 范围 | 责任 |
|------|------|
| 代码模块 | 读取整形済数据，执行业务规则，返回 DataFrame |
| 连携设置 / config | 是否调用函数、调用顺序、返回 DataFrame 的保存名、保存路径、文件形式 |

RD / BD / DD 描述代码模块时：

- 可写返回 DataFrame 的内容。
- 可写字段如何派生。
- 可写公开函数接口。
- 不把输出文件名、保存路径、CSV / Excel 形式写成代码契约。

必须提到保存文件名时，应明确：

```text
戻り値 DataFrame の保存先・ファイル名・ファイル形式は連携設定の責務とする。
```

## 2. 输出文件体系

每个スタディ生成以下 7 个 Markdown source 文件。

| No. | 文件名模板 | 文書番号模板 | 文書名 |
|-----|------------|--------------|--------|
| 00 | `00_文書統制計画書_{PROCESS_NAME}.md` | DP-{STUDY_ID}-001 | 文書統制計画書 |
| 01 | `01_要件定義書_{PROCESS_NAME}.md` | RD-{STUDY_ID}-001 | 要件定義書 |
| 02 | `02_基本設計書_{PROCESS_NAME}.md` | BD-{STUDY_ID}-001 | 基本設計書 |
| 03 | `03_詳細設計書_{PROCESS_NAME}.md` | DD-{STUDY_ID}-001 | 詳細設計書 |
| 04 | `04_テスト実施記録_{PROCESS_NAME}.md` | TE-{STUDY_ID}-001 | テスト実施記録 |
| 05 | `05_トレーサビリティマトリクス_{PROCESS_NAME}.md` | TM-{STUDY_ID}-001 | トレーサビリティマトリクス |
| 06 | `06_文書統制報告書_{PROCESS_NAME}.md` | DR-{STUDY_ID}-001 | 文書統制報告書 |

默认 `{PROCESS_NAME}` 可使用 `CombineProcess`，也可替换为该スタディ的处理名。

所有文件初版统一：

- `版数`: `1.0`
- `文書ステータス`: `Draft (レビュー待ち)`
- 変更履歴只保留 `1.0` 一行
- 変更内容以 `新規作成。` 开头

## 3. 代码事实抽取规则

### 3.1 公开函数识别

从目标 Python 文件中识别公开函数：

- 顶层 `def`。
- 被 config / pipeline 调用的函数。
- 返回 DataFrame 或业务结果的函数。
- 函数名不以下划线开头。

生成 02 BD 时，必须写 `公開処理インタフェース`。

公开接口至少包括：

| 项目 | 内容 |
|------|------|
| IF-ID | IF-01, IF-02... |
| 対応機能 | F-xx |
| 関数名 | 公开函数名 |
| 引数 | 参数名 |
| 引数の指定形式 | 字符串表名 / DataFrame / 未指定等 |
| 戻り値 | `pandas.DataFrame` 或实际返回型 |

BD 可以写公开函数名、参数名、参数指定形式、返回值型。

BD 不写：

- 内部算法。
- 内部排序 key。
- 临时列具体值。
- 配置表具体单元格。

### 3.2 输入数据源抽取

从以下代码结构抽取输入：

- `getFormatDataset(...)`
- `read_csv(...)`
- `read_excel(...)`
- config 读取函数
- DataFrame 参数
- 固定输入表名

对外文档中优先使用整形済数据名。

建议命名：

```text
F-{SOURCE_NAME}
```

示例：

- `SOURCE_A` → `F-SOURCE_A`
- `SOURCE_B` → `F-SOURCE_B`
- `EVENT` → `F-EVENT`

如果原始代码没有 `F-*` 命名，不强行臆造复杂业务名，只用“整形済 {SOURCE_NAME} データ”。

### 3.3 字段抽取

从以下代码结构抽取字段：

- `df[['COL1', 'COL2']]`
- `df['COL']`
- `merge(..., on='KEY')`
- `sort_values(by=[...])`
- `drop_duplicates(subset=[...])`
- `loc[...]`
- 新增列赋值

字段出现层级：

| 文档 | 字段名使用 |
|------|------------|
| RD | 原则上不写具体字段名，只写业务概念 |
| BD | 可写关键输入/输出字段和业务规则字段 |
| DD | 必须写字段表和处理字段 |
| TE/TM | 可写用于测试和追踪的字段 |

### 3.4 返回契约抽取

从代码中确认：

- 返回类型。
- 是否 `fillna('')`。
- 是否 `astype(str)`。
- 是否保留全列。
- 是否新增派生列。
- 异常输入时的行为。

常见返回契约：

```text
戻り値は pandas.DataFrame とする。
欠損値は空文字列として扱う。
出力項目は一貫した文字列形式とする。
```

## 4. 文档粒度分层

### 4.1 00 DP: 文書統制計画書

写：

- 目的。
- 背景。
- 适用范围。
- 7 文书体系。
- 文档责任。
- 命名和版本规则。
- レビュー・承認ゲート。
- トレーサビリティ運用。
- 変更管理。
- リスクと対策。
- 完了判定。

### 4.2 01 RD: 要件定義書

RD 写 WHAT，不写 HOW。

写：

- 背景、目的、适用范围。
- 业务处理单位。
- 解決すべき業務課題。
- FR。
- NFR。
- AC。
- 数据要件。
- レビュー/承認。

不写：

- 公开函数名。
- 具体代码式。
- 内部排序方式。
- 临时列名和内部 key。
- 具体实现技巧。

例外：

- 可写 `DataFrame` 作为返回值载体概念。
- 可写连携设置文件名，但必须说明保存文件名、保存先、文件形式由连携设置负责。

### 4.3 02 BD: 基本設計書

BD 写外部规格和业务规则。

写：

- F-xx 功能列表。
- `公開処理インタフェース`。
- 入出力仕様。
- R-xx 业务规则。
- 要件トレーサビリティ。
- 設計レビュー観点。

不写：

- 内部算法。
- 代码中临时 key 的具体值。
- A 组现行实现技巧。
- 设置表具体单元格。

关键规则：

- BD 必须足够 B 组独立实现。
- BD 不能按 A 组代码反推。
- BD 可以写函数接口，因为这是连携设置调用所需外部契约。

### 4.4 03 DD: 詳細設計書

DD 写现行实现的内部规格。

写：

- 対象モジュール。
- 実装方針。
- 每个公开函数的签名、输入、输出、异常、处理流程。
- 字段表。
- 派生逻辑。
- Mermaid 流程图。
- サンプルデータ。
- テスト仕様。
- 要件-設計-実装-試験トレーサビリティ。

DD 可以写现行实现细节。

如果现行实现和 BD 业务意图存在差异，应明确：

```text
現行実装では ...
業務意図では ...
A/B 比対で検知する。
```

### 4.5 04 TE: テスト実施記録

TE 写测试计划和执行记录栏。

初版阶段：

- `実施日`: `未実施（初版作成時点）`
- `実測結果`: `未実施`
- `判定`: `Pending`

写：

- TC-ID。
- 対応要件ID。
- 期待結果。
- 証跡ID。
- 証跡ファイル/URL。
- 不具合・課題記録。
- 判定基準。
- 承認記録。

不要伪造已执行结果。

### 4.6 05 TM: トレーサビリティマトリクス

TM 写严格追踪。

写：

- Trace ID。
- 要件ID。
- 要件概要。
- 基本設計。
- 詳細設計。
- 実装。
- テストID。
- 証跡ID。
- 戻り値/連携観点。
- 状態。

状态：

- Draft Baseline 可为 `Open`。
- Final Close 前至少应为 `Verified`。

证跡 ID 必须逐项列举，不使用范围写法。

### 4.7 06 DR: 文書統制報告書

DR 写初版整备报告。

写：

- 報告目的。
- 実施概要。
- 7 文书状态。
- トレーサビリティ評価結果。
- レビュー・承認実績。
- Git 履歴との整合。
- 課題・是正方針。
- 総合判定。
- 次アクション。

必须说明：

- 当前是 Draft Baseline。
- G1〜G4 未实施或保留。
- TE 尚未実施。
- 不是 Final Close。

## 5. 业务意图 vs 现行实现

### 5.1 判断原则

每条业务规则都要判断：

| 类型 | RD/BD 写法 | DD/TE/TM 写法 |
|------|------------|---------------|
| 现行实现等于业务意图 | 可直接规格化 | 写具体实现 |
| 现行实现只是实现手段 | 写业务意图 | 写实现手段 |
| 现行实现存在边界差异 | 写业务意图和前提 | 写现行实现与检知 TC |

### 5.2 常见危险模式

以下代码形态常常是实现手段，不应直接写成 BD 业务规则：

- 多列字符串拼接。
- 临时排序 key。
- 固定高优先级数值。
- 字符串切片作为排序依据。
- `drop_duplicates(keep='first')`。
- `fillna('').astype(str)`。

这些内容可在 DD 写，但 BD 要转化为业务语言：

- 代表行採用。
- 優先順位。
- 値を持つ項目を採用。
- 前提違反として扱う。
- 欠損値を空欄として扱う。

### 5.3 前提違反数据

如果业务前提是“互斥”“唯一”“同一代表行中不会同时有值”等，应设计专门 TC 检知：

- 正常数据：A/B 应一致。
- 前提違反数据：A/B 可能出现差分，差分本身是有效发现。

## 6. ID 体系生成规则

### 6.1 FR

FR 按业务要件编号。

推荐结构：

- FR-01〜FR-04: 主要数据处理和输出质量。
- FR-05〜FR-08: 派生、代表行、判定等业务规则。
- FR-09: 工程連携。
- FR-10: 追跡可能性。

实际数量可按目标スタディ调整，但必须在 RD/BD/DD/TE/TM 中闭合。

### 6.2 NFR

推荐至少包含：

- 性能。
- 品質。
- 堅牢性。
- セキュリティ。
- 監査性。

### 6.3 F / R

BD 中使用：

- `F-xx`: 功能。
- `R-xx`: 业务规则。

F/R 必须能追踪到 FR。

### 6.4 TC / EV

TC 应覆盖：

- 正常系。
- 异常系。
- 业务派生。
- 代表行。
- 判定。
- 工程連携。
- トレーサビリティ。
- 性能。
- セキュリティ / 監査性。
- 前提違反检知。

EV-ID 必须稳定、可逐项追踪。

示例：

- `EV-TC-001`
- `EV-PERF-001`
- `EV-SEC-001`
- `EV-AUD-001`

## 7. 术语、表记与禁止事项

### 7.1 日语术语

生成日语文档时，优先使用日本 IT 界和临床数据处理文档中自然的词。

推荐：

- `スタディ`
- `本処理`
- `処理機能`
- `戻り値`
- `戻り値 DataFrame`
- `後続工程への引き渡し`
- `公開処理インタフェース`
- `代表行`
- `代表パターン`
- `代表症例パターン`
- `接尾辞`
- `保持`

避免：

- `研究`（日语交付文档中统一用 `スタディ`，中文内部说明可用“研究”）
- `返却`
- `機能群`
- 不自然的直译词。

### 7.2 背景信息隐藏

对外交付的 00-06 中不得出现：

- 医院名。
- 具体主导机构。
- 可识别研究机构的背景描述。
- `病院`
- `主導する`
- `医療機関`

需要写设施时，用中性表达：

- `実施施設`
- `施設名`

### 7.3 输出文件名表述

RD/BD/DD 中不要把 config 生成的文件名写成代码输出契约。

可以写：

```text
戻り値 DataFrame の保存先・ファイル名・ファイル形式は連携設定の責務とする。
```

TM / TE / DR 如需说明连携观点，可写在 `戻り値/連携観点` 或备注中。

## 8. 版本与变更履历规则

初版统一：

- 页眉 `版数`: `1.0`
- `文書ステータス`: `Draft (レビュー待ち)`
- 変更履歴只保留一行。
- 変更内容以 `新規作成。` 开头。
- 不保留中间修订历史。

06 成果物状态：

- `現行版 = 1.0`
- `状態 = 新規作成`

## 9. 生成顺序

建议按以下顺序生成：

1. 解析目标函数文件，抽取公开函数、输入表、字段、返回契约、现行实现行为。
2. 读取本 guide，确认叙事口径、分层规则和禁止事项。
3. 生成 01 RD，锁定 FR/NFR/AC。
4. 生成 02 BD，写 F/R/IF 和业务规则。
5. 生成 03 DD，写代码级详细设计和测试规格。
6. 生成 04 TE，写 TC 计划和 Pending 状态。
7. 生成 05 TM，闭合 FR/NFR → BD/DD/Code/TC/EV。
8. 生成 00 DP，写 7 文书统制规则。
9. 生成 06 DR，写 Draft Baseline 判定和未完了项。
10. 运行验收检查，必要时修正。

## 10. 验收检查清单

### 10.1 文件与版本

- 00〜06 共 7 个 Markdown 文件存在。
- 每个文件页眉 `版数` 为 `1.0`。
- 每个文件有 `文書ステータス | Draft (レビュー待ち)`。
- 每个文件的変更履歴只有 `1.0` 一行。
- 変更履歴内容以 `新規作成。` 开头。
- 06 成果物表中所有文件均为 `1.0 / 新規作成`。

### 10.2 引用闭合

- FR 在 RD/BD/DD/TE/TM 中可追踪。
- NFR 在 RD/DD/TE/TM 中可追踪。
- TC 在 DD/TE/TM 中一致。
- EV-ID 在 DD/TE/TM 中一致。
- 证跡 ID 逐项列举，不使用范围写法。

### 10.3 分层正确

- RD 不出现函数名。
- RD 不出现内部排序 key。
- BD 出现公开函数接口，但不写内部算法。
- DD 可以写代码实现，但实现差异必须标明为现行实现。
- TE/TM 中可以写用于检知差分的现行实现说明。

### 10.4 禁止词检查

日语 00-06 中不得出现：

- `研究`
- `病院`
- 具体机构名。
- `主導する`
- `医療機関`
- `機能群`

RD/BD 中不得出现：

- 固定内部 key 值。
- 内部排序用临时列值。
- 字符串切片等实现细节。

### 10.5 表格格式

- Markdown 表格列数一致。
- 代码块内表格不参与列数检查。

## 11. 推荐验证命令

以下命令中的路径按目标スタディ替换。

```powershell
rg -n "^\\| 版数 \\||^\\| 1\\.[1-9] \\||改訂済" -- "{DOC_ROOT}/MarkDown"
```

预期：

- 只能看到 `| 版数 | 1.0 |`
- 不应看到 `1.1` 以上的変更履歴。
- 不应看到 `改訂済`。

```powershell
rg -n "研究|病院|主導する|医療機関|機能群" -- "{DOC_ROOT}/MarkDown"
```

预期：

- 无输出。

```powershell
rg -n "EV-[A-Z]+-[0-9]{3}\\.\\.|EV-[A-Z]+-[0-9]{3}〜" -- "{DOC_ROOT}/MarkDown"
```

预期：

- 无输出。

## 12. 最终判断原则

agent 生成或修正文档时，遇到不确定内容按以下优先级判断：

1. 先保护 A/B 比对有效性。
2. RD/BD 写业务意图，不反推现行实现。
3. 连携设置负责保存文件名、保存路径、保存形式。
4. 代码模块负责返回 DataFrame 或业务结果对象。
5. 公开函数接口属于 BD 可写的外部契约。
6. 内部排序 key、内部数据结构、实现技巧属于 DD/TE/TM。
7. 不暴露机构、医院、主导方等敏感背景。
8. 00-06 是 Draft Baseline，不是 Final Close。
