# COSMOS_GC 文档体系 — 内部背景共识

> ⚠️ **本文件用于内部对齐**：记录 `studySpecific/COSMOS_GC/20_Doc/MarkDown/` 文档体系的真实创作背景与工作约束。
> **不属于对外交付的 7 文档体系**（DP / RD / BD / DD / TM / TE / DR）。仅供研究负作业者本人以及协助者（AI / 同事）对齐使用。

---

## 1. 项目与文档体系定位

### 1.1 本文件 (`_BACKGROUND_INTERNAL.md`) 的定位

- 研究负作业者 + AI 的**思路对齐文档**
- **独立于具体研究本身**（不是 COSMOS_GC 研究的产物）
- **不属于纳品物**，也不在对外的 7 文档体系中
- 本研究完成后，**考虑抽象为可复用的 skill**（脱离 COSMOS_GC，作为通用模板供其他研究使用）

### 1.2 COSMOS_GC 研究的定位

- **独立的研究**，不是 COSMOS 多コホート 研究下的一个 cohort
- 本套文档体系 / 模板 **不与其他研究复用**（每个研究独立维护自己的 RD/BD/DD/TM/TE/DP/DR）

### 1.3 文档载体（`.md` 与 `.xlsx` 的关系）

- `20_Doc/MarkDown/*.md` = **source**（源文件，主要工作介质）
- `20_Doc/*.xlsx` = **纳品物**（用于公司内部交付，要求视觉**有层次 + 美观**）
- 工作流程：先改 `.md`，再据此生成 / 同步 `.xlsx`，最后用 `.xlsx` 纳品

### 1.4 合规边界

- **不对应**任何法规要件（GxP / CDISC SDTM / ICH / PMDA 等）
- 仅用于公司**内部纳品**

## 3. 双重身份

研究负作业者（= 本文件读者）同时担任两个角色：

- **研究作业者**：编写 01 RD、02 BD（同时承担 DP / DR / TM 等共同作成部分）
- **A 组代码制作者**：编写 A 版 03 DD、04 TE 以及对应代码（即现存的 `VC_BC05_studyFunctions.py`）

---

## 4. A/B 双实装比对的结构

01 RD + 02 BD 作为**两个独立小组的实装规格**，用于事后比对：

- **A 组**：研究负作业者本人。代码 / DD / TE 已存在。
- **B 组**：**不懂业务、不懂本研究**的程序员。只看 01 / 02 写代码。

两组代码对同一份数据跑出来的输出一致 → 视为 A 组实装通过事后检验。

---

## 5. 对 01/02 的硬约束

A/B 比对的有效性，靠 01/02 满足以下 4 条约束来保障：

| 约束 | 真实动机 |
|---|---|
| 读者「只懂代码、不懂业务」为前提 | B 组就是这样的人 |
| 范围对齐：代码契约 vs config 契约 | B 组只实装代码层的契约，config 那边不归他管 |
| RD = WHAT，BD = 业务规则 R-xx 细节 | RD 锁定不变，BD 是 B 组独立实装的唯一依据 |
| 措辞必须在代码中可验证 | 防止 B 组靠业务直觉补完，否则 A/B 比对失效 |

### 5.1 读者画像 — 具体操作规则（对应约束 1 + 4）

- 优先使用代码能**直接验证**的标识符：表名（`F-PAT` / `F-IE` / ...）、字段名（仅 BD / DD 出现，RD 不写具体字段名）、函数名
- 业务术语（如「転帰」「初回投与」）出现时必须**附代码对应**：转化为字段名引用或派生规则描述
- **不引入代码中不存在**的业务命名：例如「コホート登録情報」/ `F-COHORTREG` 是 config 范围的命名，不属于代码契约，不应出现在描述代码模块的文档里
- 章节命名按**代码视角**组织：例如「業務フロー」当代码不是一条流程时，改成「処理単位」，让读者能从函数定义直接对照

### 5.2 代码契约 vs config 契约（对应约束 2）

- 代码模块的契约**止于返回 DataFrame**
- 输出文件名（如 `F-COHORTREG.csv`）、保存先、文件格式由 `COSMOS_GC_OperationConf.xlsx` 决定，**不属于代码契约**
- 描述代码模块的文档（RD / BD / DD）中：
  - ✅ 可写：返回的 DataFrame 包含哪些字段、字段如何派生
  - ❌ 不写：输出文件名、保存位置、文件格式
- 文档中确实需要提到输出文件名时（如 RD §1.3 适用范围），应**明示其归属**：「ファイル名・保存先は連携設定 (`COSMOS_GC_OperationConf.xlsx`) で定義され、本書の対象外」

### 5.3 粒度分层（对应约束 3）

| 文档 | 写什么 | 不写什么 |
|---|---|---|
| **RD（要件定義書）** | 业务要件 (WHAT) | 字段名、函数名、算法 |
| **BD（基本設計書）** | 外部仕様（业务规则 R-xx、I/O 责务）、B 组独立实装的依据 | 函数签名、内部算法 |
| **DD（詳細設計書）** | 内部仕様（函数签名、字段表、算法）、A/B 各自一份 | — |

## 6. 当前任务的真正含义

> **把 01/02 写得让 B 组能独立写出与 A 组数据等价的代码——同时保留发现 A 组代码 bug 的可能性。**

不是「打磨文档美观度」，而是上述目标。

## 7. 结构性风险（持续提请留意）

研究负作业者既是裁判又是运动员。打磨 02 BD 的业务规则 R-xx 时，存在一个微妙的陷阱：

> 如果 BD 的规则写得「按 A 组实装反推」，B 组写出来必然和 A 组一致——但这种「一致」是规格强迫的，已经不能再检验 A 组代码的正确性了。

### 7.1 具体例子

[VC_BC05_studyFunctions.py:153](studySpecific/COSMOS_GC/VC_BC05_studyFunctions.py)：

```python
cohort_df['COHORT_ALL'] = cohort_df[['COHORT', 'COHORTA', 'COHORTB']].agg(''.join, axis=1)
```

- A 组实装：**字符串拼接**
- 如果 BD R-01 写「3 列字符串拼接」→ B 组也只能拼接 → A/B 必然一致（**比对失效**）
- 如果 BD R-01 写「相互排他前提下，取唯一非空值」→ B 组可能写成 `select non-empty` → 当数据违反相互排他前提时，A 组生成异常长字符串、B 组取第一个非空值 → **比对暴露这个边界情形**

### 7.2 判断原则

打磨 02 BD 的每一条 R-xx 规则时，必做「**实装锁死 vs 业务意图**」判断：

- **优先业务意图**：让 B 组能从业务逻辑推出实装
- **避免实装细节**：除非业务意图本身就是「按这种方式处理」
