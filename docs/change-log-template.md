# 更新履歴テンプレート / Change Log Template

このテンプレートは、SDTM Mapping 仕様書、OperationConf、DomainsSetting、CodeList、出力 CSV などの変更履歴を、study を問わず同じ粒度で残すための共通フォーマットです。

新しい履歴を作成する agent は、既存の確定済み履歴ファイルを直接書き換えず、新しい日付の履歴ファイルを作成してください。

## 使い方

- Study 固有の履歴は `studySpecific/<STUDY_ID>/20_Doc/更新履歴_YYYYMMDD.txt` に作成する。
- `YYYYMMDD` は原則として履歴ファイルを作成する日付にする。
- 本文の `日付` は、実際に変更を適用した日付を記載する。作成日と変更日が異なる場合は `文書作成日` を追加する。
- 1 ファイルに 1 版を記載する。複数の独立した変更を同日に行った場合は、同じ版の中で対象領域ごとに分ける。
- 判断理由、変更前後、影響、未変更事項、確認結果を分けて書く。
- 不明な項目は削除せず、`未確認` または `該当なし` と明記する。
- 出力件数、テスト ID、定義書バージョン、レビュー資料名など、後から検証に使える根拠を優先して残す。

## 記載粒度の基準

- `背景／根拠`：なぜ変更する必要があったか。レビュー指摘、UAT、総合テスト、定義書改訂、仕様確認など。
- `変更内容`：どこを、どう変えたか。Domain、項目、条件、固定値、CodeList、SORTKEYS などを具体的に書く。
- `影響`：データ件数、出力値、出力順、後続工程、比較テストへの影響を書く。
- `未変更事項`：誤解されやすいが変更していないものを書く。
- `確認結果`：実行した確認、比較結果、残課題を書く。

## テンプレート

```text
更新履歴（Change Log）

版数：vX.X
日付：YYYY-MM-DD
文書作成日：YYYY-MM-DD（変更日と異なる場合のみ記載）
Study：<STUDY_ID>
対象：<対象文書／設定ファイル／成果物>
変更区分：<新規追加／修正／削除／整理／仕様準拠／テスト指摘対応>
影響範囲：<Format-CodeList ステップ／Mapping ステップ／DomainsSetting／出力CSV 等>
変更理由：<レビュー結果／UAT結果／総合テスト結果／定義書準拠 等>
参照元：<テストID、レビュー資料、定義書バージョン、指摘票、メール日付など>

[背景／根拠]
- <変更が必要になった背景>
- <確認された事象、レビュー指摘、テスト結果、仕様差分など>
- <判断に使った資料や前提>

[変更内容]
[<Domain／対象領域／設定シート>]
- <変更種別>：<対象項目／対象設定>
  - 変更前：<旧値／旧条件／旧ロジック>
  - 変更後：<新値／新条件／新ロジック>
  - 条件：<出力条件、SEL/FIX、対象レコード、対象 visit など>
  - 根拠：<定義書、テスト結果、レビュー指摘など>
  - 備考：<補足。なければ該当なし>

[影響]
- データ件数：<変更あり／なし。例：1752 -> 1701>
- 出力値：<変更あり／なし。対象項目を記載>
- 出力順：<変更あり／なし>
- 後続工程：<影響あり／なし。PS01、PS02、M5 package など>
- テスト観点：<再確認すべき CSV、Domain、チェックID>

[未変更事項]
- <明示的に変更しない項目、条件、Domain>
- <変更対象外と判断した理由>

[確認結果]
- <実行した確認コマンド、ステージ実行、差分確認、レビュー確認など>
- <確認結果の要約>
- <残課題があれば記載。なければ「残課題なし」>
```

## 簡易版テンプレート

小さい変更で詳細な背景や影響が不要な場合は、以下を使用してもよい。

```text
更新履歴（Change Log）

版数：vX.X
日付：YYYY-MM-DD
Study：<STUDY_ID>
対象：<対象文書／設定ファイル／成果物>
影響範囲：<対象ステップ／Domain／CSV>
内容：<変更の要約>

[変更内容]
- <変更種別>：<対象項目>
  - 変更前：<旧値／旧条件>
  - 変更後：<新値／新条件>
  - 根拠：<レビュー指摘、テスト結果、定義書など>

[影響]
- <データ、出力、後続工程への影響>

[確認結果]
- <確認内容と結果>
```

## Agent 向けチェックリスト

- 既存の確定済み `更新履歴_*.txt` を上書きしていない。
- ファイル名の日付と本文の日付の意味が矛盾していない。
- 変更理由が、レビュー、テスト、定義書、仕様判断のいずれかとして追跡できる。
- 変更前と変更後が具体的に書かれている。
- データ件数、出力順、後続工程への影響が明記されている。
- 「変更しないもの」がある場合は `未変更事項` に残している。
- 確認結果に、実行したステージ、比較、テスト ID、または未確認理由が書かれている。
